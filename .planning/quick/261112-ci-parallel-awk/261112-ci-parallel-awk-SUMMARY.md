# Quick 261112-ci-parallel-awk: second awk gate as a parallel job, stable `gate` check, a timeout on every job

Local work only: no push, no PR, no tag, no remote or settings change. It rides with the next owner-authorised publication.
CI evidence for this change is unverified until the owner authorises a push (D-64). The numbers below are an estimate from measured step times, not a CI run.

## What changed

`.github/workflows/gate.yml` is three jobs instead of one:

| Job | Contents | Timeout |
|-----|----------|---------|
| `gate-gawk` | checkout, tool versions, cc65 apt install, `Gate` (image default awk), `Range audit` (pull requests only), gcc build and conformance | 25 min |
| `gate-mawk` | checkout, tool versions, cc65 apt install, the gate under the other awk (unchanged PATH shim, selection logic and explicit apt fallback), clang build and conformance | 25 min |
| `gate` | named exactly `gate`; `needs` both; `if: always()`; one step with env `needs.<job>.result` and `test "$VAR" = success` lines; no checkout | 5 min |

Kept as required: `actions/checkout` pinned to the same full SHA with `fetch-depth: 0` and `persist-credentials: false`, `permissions: contents: read` at the top (and now in each job), no new third-party action, no cache, `ubuntu-24.04`, the `sh -eu {0}` shell, the concurrency block.
The aggregator reads each needed job's result because a skipped or cancelled needed job would make a needs-only job skip, and a skipped required check reads as passing. Only the result `success` passes.

Split choice (from the measured step times of the two Phase 4 runs): gawk job = gate + range audit + gcc build (441 s and 545 s expected), mawk job = second awk run + clang build (423 s and 516 s). The brief's first split (both builds in the gawk job) would be about 521 s and about 665 s for that job against about 343 s and 396 s for the other; this one is within 20 to 30 s.
The clang step stays under the default awk, as in the single job, so no evidence moved between awk implementations.
Expected run wall about 450 s (run 1 basis) to 555 s (run 2 basis) against 856 s and 1051 s; total runner seconds about the same. Recorded in `docs/ci-timings.md`, section "Parallel second awk job (quick task, unverified on CI until pushed)", with the statement that the owner hand-off is unchanged: the ruleset requires `gate`, and the aggregator carries that exact name.

`scripts/lib/workflow-rules.awk` and `scripts/workflow-check`:

- Per-job state replaces the file-level state (steps, checkout, runs-on, cc65 order). `WF_NO_TIMEOUT` (new): every job needs `timeout-minutes`, a whole number from 1 to 30, in any workflow file.
- In gate.yml: every job has its own `permissions: contents: read` (`WF_NO_PERMISSIONS`) and a `runs-on` (`WF_RUNNER`); every job but `gate` has a checkout (`WF_MISSING_FETCH_DEPTH`) and a step that
  runs the gate command, a `run` that is, or a run block that holds a line, exactly `sh scripts/check` (`WF_NO_GATE_STEP`); in each job that runs it, an apt install of cc65 comes first
  (`WF_NO_CC65_STEP`, now per job).
- `WF_AGGREGATOR` (new): the job `gate` exists, is named `gate` (no other job may be), needs exactly the other jobs, has `if: always()`, has an env entry `needs.<job>.result` and a `test "$VAR" =
  success` line for every needed job; its run block holds only those test lines and plain echo lines, it has no one-line run value, and no step in it has an `if` key. The expression
  `needs.<job>.result` is allowed in that job only.
- Stale step-list indices that would have read the `needs` list items as steps were reset when a job or the steps block ends (found while designing the aggregator; no behaviour change for the old single-job file).

Controls and selftests: 17 new negative mini-roots (31 in all), the 14 old ones regenerated from the new file (each differs from it by the same mutation as before, `ok-gate` is a byte copy, still
checked by `CONTROL_DRIFT`), and 14 new selftests, each deleting one tagged rule line (or the two lines of the skipped-as-success case) in a scratch copy and requiring its control to flip:
`mutation-workflow-timeout`, `-job-runner`, `-job-perm`, `-job-checkout`, `-job-gate`, `-agg-missing`, `-agg-name`, `-agg-if`, `-agg-needs`, `-agg-result`, `-agg-line`, `-agg-oneline`, `-agg-step-if`,
`-agg-skipped` (an aggregator that treats skipped as success). `mutation-workflow-cc65` now includes the `no-cc65-step-mawk` control (the rule is per job). The shared helper was shown not to be
vacuous: a deliberately wrong control pairing made the selftest FAIL.
The mini-roots were regenerated by a throwaway generator kept outside the repository (it copies the real file and applies one mutation per case); the mutations are visible as diffs against `ok-gate`.

## Deviations from Plan

None that change scope. Notes:

1. **Split differs from the brief's example.** The brief suggested balancing with the measured numbers; the best balance puts the gcc build with the gate and the clang build with the second awk run, not both builds with the gate. Reason and numbers above.
2. **Job-level permissions are enforced as well.** The brief said the aggregator gets `permissions: contents: read`; every job has it now and the checker requires it per job (the top-level block still applies and is still required).
3. **Rule 3 fix inside the checker.** The old rules kept `stepind` after the steps block ended, which would have misread the `needs` list of the next job as steps. Fixed in the same commit.
4. `STATE.md` and `ROADMAP.md` were not touched: a quick task outside the phase plans, as for the earlier quick tasks. `.planning/state.json` stays untouched and uncommitted.

## Notes for the orchestrator

- With `if: always()` the aggregator also runs when a pull-request run is cancelled by the concurrency group (a newer push). It then fails with result `cancelled`, which is correct for a superseded run (the newer run has its own `gate`); it is not a defect.
- The ruleset hand-off is unchanged: it must require `gate` (the aggregator). Requiring only `gate-gawk` or `gate-mawk` would be a regression; they need not be listed. Whether an existing ruleset that names `gate` matches the aggregator is confirmed only by a real run after a push.
- After a push, record the first run with `sh scripts/ci-timings RUN_ID` (one entry per job) and review it against the expected 440 to 550 s per work job, the duplicated cc65 and checkout cost, and whether the aggregator goes red when a work job fails.
- Possible later levers, not applied: the second awk run paired with clang, a skip of `sanitizers` in the second run, the two compiler builds as their own jobs.
