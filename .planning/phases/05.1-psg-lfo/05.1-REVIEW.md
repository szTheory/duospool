I wrote an independent event-driven reference of the LFO pair from D-184, D-185 and D-219, and it agrees with `ds_psg_advance` on every state I drove. The three warnings are about evidence and claim discipline around the code, not the code.

- **WR-01:** the LED-AUD-0011 statement has a last clause that is not conditioned on the LFO applying, and the model contradicts it for CTL 0.
- **WR-02:** the ER-15 `lfo_wrap` disputed point is never detected by `audio-check`; a MAN row on a wrapped sum passes.

## Warnings

### WR-01: LED-AUD-0011 states the coupled select-1 step for every TRG 0, but the model couples it only while the LFO applies

**File:** `ledger/entries/LED-AUD-0011.toml:9` (statement); model at `src/core/psg.c:114-129` (`chan_period`)
**Issue:**
- The statement ends: "TRG 1 sets widx[1] to 0, freezes select 1 and holds w at wave[1][0] whatever widx[1] is; TRG 0: select 1 steps every d x F1e x FLFe."
- That last clause is its own semicolon clause, outside the "while LF CTL != 0 and select 0 and 1 have chON 1" qualifier of the clause before it. `chan_period` multiplies by FLFe only when `lfo_applies()` is true. With CTL 0, or with select 0 off, select 1 steps every d x F1e.
- Failure scenario 1: the lfo_release scene (CTL 0, TRG 0, F1 = 256) steps select 1 every 6 x 256 = 1,536 clocks. Its `rel` row relies on exactly that plateau length (60,000-clock window, 32 plateaus). A reader of the statement expects 6 x 256 x FLF.
- Failure scenario 2: `psg_lfo_trg` expects, with FLF 150 still set, an uncoupled next step 768 (6 x 128) after the R9 $00 write at 250,000, where the statement says 115,200.
- The entry is `assumed`, but a ledger statement is the project's record of what the model does. ER-14 and D-218 say the statement may claim only what the gate shows. The statement as written is false for CTL 0.
- The same clause in RULES (`aud11-d`: "TRG 0 lets select 1 step every d x F1e x FLFe") carries the same gap. It was inherited from the Phase 5 planned statement, where the preceding "modulation applies while ..." made it conditional. C-10 flattened that grammar when it moved the clauses back.
- The assumption field has the right qualifier ("or + d x F1e x FLFe when coupled"), but only for the restart.

**Fix:** state the condition on the clause itself, and keep the statement short:
```toml
statement = "... TRG 1 sets widx[1] to 0, freezes select 1 and holds w at wave[1][0] whatever widx[1] is; with TRG 0 select 1 steps every d x F1e, and every d x F1e x FLFe while LF CTL != 0 and select 0 and 1 have chON 1. Modelling assumption."
```
Adjust the `aud11-d` and `d184-d` RULES text the same way.

### WR-02: The ER-15 `lfo_wrap` disputed point is not detected by audio-check; a MAN row on a wrapped sum passes

**Files:**
- `tests/audio/DISPUTED:15` (the `lfo_wrap` marker, "an LFO sum leaving 12 bits")
- `tests/audio/DISPUTED:4-5` (header: markers are found in the row for f=0, flf=0, nf=0, reg=RA..RF, R0 select 6 or 7 and the P8-10 sum 15; every other marker needs an explicit `mark=`)
- `scripts/lib/aexp-rules.awk:49-54` (`fprime`), `:360-372` (lfo_static arithmetic), `:382-392` (lfo_dynamic arithmetic), `:438-448` (disputed-marker rule)

**Issue:**
- ER-15 and D-184 make the wrap and the 0 -> 4096 rule "ASSUMED rows only"; 05-CONTEXT line 365 says "no row wraps the 12-bit sum".
- Phase 5.1 is the first phase to put `f`, `w`, `shift`, `w1` and `w2` into `.aexp` rows. The lint recomputes F' from them and checks `d = k x F'`, but it never asks whether `f + (w << s) - (16 << s)` stays within 0..4095. The rule that keeps wrapped rows ASSUMED depends on the author remembering `mark=lfo_wrap`.
- Failure scenario (probed): a future lfo_static row `f=16;w=$00;shift=0;k=2;d=8192` with class MAN gets no violation from `audio-check`. The group would then claim a manual literal for a convention the project calls disputed, and the README sentence ("the 12-bit wrap ... labelled assumptions") would be false for that row.
- Today every committed row is wrap-free (F' 512 to 640, 520, and 200 and 184 for dyn), so nothing is wrong now. The gate does not stop the next one.

**Fix:** in `aexp-rules.awk`, where `fprime` is already called, compute the raw sum `f + w*p - 16*p` (and for w1 and w2 with p = 1). 
When it is below 0 or at least 4096, add the marker `lfo_wrap` to the row's marker set, so that rule `rule-audio-disputed-mark` fires for MAN groups. Add a mini-root negative control (as for f=0) with an `--expect AUDIO_DISPUTED_POINT` run on a row like the probe above, and update the `DISPUTED` header line.

### WR-03: Nine RULES lines name kinds whose groups cannot fail when the clause fails

**Files:** `tests/audio/RULES` lines 27 (`aud04-g`), 35 (`aud06-c`), 53 (`aud11-c`), 54 (`aud11-d`), 77 (`d184-d`), 105 (`d220-b`), 107 (`d219-b`), 109 (`rf4-a`), 110 (`rf5-a`); `scripts/lib/aexp-rules.awk:564-577` (coverage is per kind, any file, any kill other than AF0)

**Issue:** ER-17 means a `row` clause has a group that would fail if the clause failed. For these lines that does not hold, in three ways.
- **(i) Step length: `aud06-c`, `aud11-d`, `d184-d` (NEED `lfo_dynamic`).**
  - The dyn judge reads only run structure from the stream (complete cycles, runs of A or B, one straddling cycle, interior runs of at least `AU_LFO_MIN_RUN` = 40, `audiokinds.c:1221, 1766`). The literals `step=115200`, `f2` and `flf` are checked by the lint and never compared with the stream.
  - FLF 0 read as 256 (step 196,608) passes. The 05.1-02 mutant re-run records this as W26 surviving at guest level. By the judge's rules so does any FLF from about 120 to 255: the half table lasts 7,400 to 16,300 samples, both lengths occur, and interior runs stay at 40 or more. I derived that range and did not run it.
  - Only `psg_lfo_trg` (115,200 at C level) discriminates. The RULES text says this, but the status and NEED say `row lfo_dynamic`.
- **(ii) TRG freeze and index reset: `aud11-c`, `d219-b`, `rf4-a` (NEED `lfo_static`).**
  - In lfo_static select 1 is silent (R5 $00) under TRG 1, and w is read at wave[1][0] whatever widx[1] is (D-231). Neither a deleted freeze nor a deleted `widx[1] = 0` can change a sample.
  - The 05.1-02 re-run records W30 (the freeze deleted) surviving every psg_lfo case. The reset half I judge unobservable by inspection (not run): the reset matters only while widx[1] != 0 when TRG 1 is written, and no scene observes that.
  - Only `aud11-c` carries a caveat ("widx[1] != 0 under TRG 1 judged at C level only"); `d219-b` and `rf4-a` do not mention the freeze or reset gap.
- **(iii) TRG-release restart: `aud04-g`, `d220-b`, `rf5-a` (NEED `cycle_phase`).**
  - C-03 chose `cycle_phase` because naming `lfo_dynamic` "would be vacuous coverage". `cycle_phase` is vacuous in the same way: psg_mod's `d_phase` and `d_rel` (`psg_mod.aexp:89, 92`) satisfy it. Probe: with the lfo_release scene and its `rel` group deleted, none of the three lines turns red.
  - This is the per-kind coarseness already noted as IN-06 in the Phase 5 review; Phase 5.1 added nine more lines that depend on it.
- Failure scenario: someone deletes `rel`, or breaks the freeze, or changes FLF handling; `audio-check` and the guest cases stay green for the clauses that claim to cover it. Only the C-level cases catch it, and RULES does not name them.

**Fix:** split each affected clause into a guest half (kind) and a C-level half that names a REQUIRED case. The `case:` form already exists and is used by `aud07-b`, `aud04-d` and `d185-c`. 
Use `case:psg_lfo_trg` for the step length and the freeze or reset, and `case:audio_lfo_release` for the TRG-release restart. Add a caveat to `d219-b` and `rf4-a`. Optionally, make a RULES row name its group (`need=scene:gid`), as IN-06 suggested.

## Info

### IN-01: The dyn judge's run-length floor is a constant calibrated to one fixture, and the row's `step`, `f2` and `flf` are decorative

**File:** `tests/conformance/audiokinds.c:1221, 1766` (`AU_LFO_MIN_RUN`); `fixtures/src/psg_lfo.aexp:75-76`
**Issue:** `AU_LFO_MIN_RUN` is 40, sized for psg_lfo's 9,600-sample half table (48 cycles of 200). The row carries `step=115200;f2=128;flf=150`, which the lint checks and the judge ignores. A second lfo_dynamic row with a different step or table length is judged against 40 cycles whatever its literal says. A shorter half table fails falsely, and a longer one gets no stricter check.
**Fix:** derive the floor from the row, for example a `minrun=` item, or compute it from `step` in the judge. Alternatively, name `step`, `f2` and `flf` lint-only in the group comment so that a reader does not take them as judged.

### IN-02: Impossible-state guard: the TRG test inside `chan_period` for select 1 is always true when reached

**File:** `src/core/psg.c:122`
**Category:** necessity
**Issue:**
- `else if (((uint32_t)inst->psg_lfo_ctl & 0x80u) == 0u)` guards the coupled step of select 1 against TRG 1. The state cannot occur: `chan_period(..., 1, ...)` is reached only from `chan_catch_up` (needs `psg_rem[1] != 0`), from `chan_start(1)` and from `fold_lfo` (needs `chan_running(1)`).
- `psg_rem[1]` is zeroed by every R9 write with TRG 1 (`psg.c:385-386`) and by every R4 write that leaves select 1 not running (`psg.c:347-348`). The restore decoder refuses a non-zero distance under TRG (`psg_frozen`, `snapshot.c`).
- `chan_start(1)` is called only after `chan_running(1)` (lines 347-350, 388), and `chan_running` includes TRG 0.
- The condition is a harmless defense in depth, so this is Info and not a Warning.

**Fix:** keep it as a statement of the invariant, but say so in the comment on `chan_period` ("called only with TRG 0 for select 1"), or drop the test.

### IN-03: Stale or overstated comments in the LFO cases and the timing notes

**Files:**
- `tests/conformance/cases/psg_lfo.toml:4-5, 11`
- `tests/conformance/cases/psg_fold.toml:11-12`

**Issue:**

- `psg_fold.toml` says "at most 600 iterations of the coupled loop per fold". `psg.c:147` and the 05.1-01 SUMMARY say at most 200 iterations plus one: a coupled step is at least d >= 3 clocks and a fold spans at most 600 clocks. 600 is the span, not the iteration count. The extreme row proves 200.
- The ci-timings row attributes part of the growth of the 388 existing cases to "the wider `psg_fold`, `psg_lfo_trg` and judges", while the next row says `psg_fold`, `psg_lfo_trg` and `psg_random_regs` together grew only +0.22 G.

### IN-04: chunk_equiv_audio_psg_lfo has 0.6 percent of margin over the guest's done state

**File:** `tests/conformance/cases/chunk_equiv_audio_psg_lfo.toml` (`until_mclk = 8000000`)
**Issue:** kind chunk_equiv refuses a deadline before the guest's DSV1 done state (D-95). psg_lfo's verdict is at 7,951,284, so the margin is 48,716 clocks, about 2.6 delay units of the fixture (18,432 each). 
Adding three units to any scene, or a CPU-timing correction of 0.6 percent, turns the case red with the D-95 message, not with a chunk defect. The failure is loud, so the cost is a confusing red, not a hole.
**Fix:** raise the deadline to 8,500,000 (about 6 percent more work in the 5-schedule case), or derive it from the done state.

## Checked and found sound (no finding)

- **Fold arithmetic (psg.c).**
  - The unsigned sum `F0 + $1000 + (w << s) - (16 << s)` lies in 3,840..8,431 and the operations are ordered so it never underflows. The 12-bit mask, the 0 -> psg_f0_as rule and `s` in {0, 2, 4} (the toy anchor, unreachable at CTL 0 because `lfo_f0` is called only while CTL is 1 to 3) all match D-184.
  - `fold_lfo` catches select 0 up to `o1 - 1`, steps select 1 with the new distance `o1 + period`, and loops, so a select-0 reload at the select-1 instant reads the new word (D-185 tie order). It composes with the per-sample folds and with the step-end rebase, and the reference confirms it.
  - Offsets stay below 600 + 6,291,456 < 2^23 (static assertion). Iterations: at most 200 + 1 for a span of 600 at d >= 3; `psg_fold` pins `ds_max_step_mclk() <= 600` (psgkinds.c:1007) and the d = 3 extreme (200 steps each, equal to 600 one-clock folds).
- **Register side.**
  - R9 with TRG 1 zeroes widx[1] and rem[1]. TRG 1 -> 0 restarts select 1 through `chan_start`, with the coupled or the uncoupled period by `chan_period`.
  - A CTL or coupling change applies at the next reload, because a pending distance is never touched (D-195).
  - UNMODELLED is no longer set. The two `psg_lfo_trg` rows were updated, and bit 6 stays defined for the DSPE layout. No other consumer of the bit exists in `src`, `tests` or `scripts`.
- **Restore (C-09, D-235, D-223).**
  - A running select 1 is bounded by `d x (DS_PSG_COUPLED_REM_MAX / 6)`, which is 6,291,456 at d = 6 and 3,145,728 at d = 3, with a static assertion that the constant divides by 6. The d = 6 bound is applied to select 1 only.
  - Reachability: a coupled distance outlives a coupling change, and after a step-end rebase it is at most one period, so the widened bound accepts no unreachable value.
  - Rows: `p-rem1over` and `p-rem1coupled` now accept, `p-rem1coupover` (maximum + 6) is refused as field, and the d = 3 rows 12,289 accept and 3,145,729 field. The divisor is read from the restoring instance, and a snapshot of the other d is refused by the profile identity first.
  - The hostile case is bounded: a restored select 1 with F1 = FLF = 1 costs at most 201 iterations per fold.
- **Epoch, serial and text.** No bump is needed.
  - `git branch -r --contains 2575af4` and `git tag --contains 2575af4` are empty, so epoch 6 is unreleased.
  - The Phase 5 ROMs write R9 only with CTL 0 (`psg_tone.s` sc_probe: $80, $00 and $7C, masked to 0), and `lfo_applies` is false for CTL 0, so every Phase 5 golden is unchanged.
  - The PSGT layout is unchanged and the decoder accepts a superset.
- **Hand literals.** I re-derived every literal and none is core-derived.
  - Period rows: 1,024, 1,088 (CTL 2: 512 + 96 - 64 = 544), 1,280 (CTL 3: 512 + 384 - 256 = 640) and 1,040 (CTL 1: 520).
  - Windows: 192 F' + 2,000 to 5 x 192 F' for each phase; phase lengths of 28, 30, 35, 29 and 28 units against 18,432 clocks per unit.
  - The `rel` words from tab_1 (24, 29, 18, ... and 1, 4, 7, ...), set=200,184 (192 + 24 - 16 and 192 + 8 - 16), step 115,200, the 21,000-sample window and the delay of 232 units after R9 $01.
  - The C-level numbers: 59,761, 175,201, 178,225 and index 6, 291,169, 196,608, 6,001 + 6 x F'.
  - The toy numbers: 1,056 for 1,088 and 1,088 for 1,280, with CTL 1 staying green. The toy anchor occurs once in `psg.c`.
- **lfo_dynamic judge.**
  - Traced by hand against the nine judge-forms rows and the real stream shape (A run, one straddling cycle, B run, one straddling cycle, A edge run).
  - Run closing at the sentinel, the interior test (`nset >= 2`) and the edge tests are right. A drop mid-run (AF2) gives a third length inside a run and fails.
