## Fixed Issues

### WR-01: LED-AUD-0011 states the coupled select-1 step for every TRG 0

**Files modified:** `ledger/entries/LED-AUD-0011.toml`, `tests/audio/RULES`
**Commit:** 59cc89a
**Status:** fixed, requires human verification (a ledger statement change)

**Applied fix:**
- The statement now conditions the step on the LFO applying. It reads "... and select 1 with TRG 0 steps every d x F1e x FLFe instead of d x F1e; TRG 1 sets widx[1] to 0, freezes select 1 and holds w at wave[1][0] whatever widx[1] is".
- The condition is the one of the clause before it, "while LF CTL != 0 and select 0 and 1 have chON 1", which is `lfo_applies()` in `chan_period`. With CTL 0 or a select off, select 1 steps every d x F1e. That is the plateau the `rel` group of lfo_release relies on (6 x 256 = 1,536 clocks) and the 768 of psg_lfo_trg.
- RULES `aud11-d` and `d184-d` carry the same condition and name the uncoupled step.
- Status stays `assumed`, evidence stays `[]`, the pin and the withheld list are unchanged.

**Other entries checked:** LED-AUD-0006 ("LFO-coupled select-1 step") and LED-AUD-0007 ("in the LFO-coupled select-1 step") already carry the condition in their wording. The README has no sentence about the step. The `chan_period` comment in psg.c is conditioned. The assumption field of LED-AUD-0011 already had the qualifier.

**Deviation (statement wording).** The statement line was 399 characters and the limit is 400 (`ledger/SCHEMA.md`), so the reviewer's text did not fit. The statement now:
- uses `w = wave[1][widx[1]]` for "w the select-1 word at its counter";
- drops the parenthetical "(masked $83)" of "R8 and R9 are stored". LED-AUD-0003 states the stored masks (R9 $83, R8 under "others $FF").
- Two new comment lines in the entry record the fix and the removed parenthetical. The model is unchanged, only the wording.

### WR-02: audio-check does not detect the ER-15 lfo_wrap disputed point

**Files modified:** `scripts/lib/aexp-rules.awk`, `tests/audio/DISPUTED`, `scripts/check`; new mini-roots `tests/audio/disputed-wrap-zero`, `-low`, `-high`, `-dynamic` and `tests/audio/ok-lfo-bounds`
**Commit:** f380f05
**Status:** fixed, requires human verification (a lint condition)

**Applied fix:**
- A new function `lfoout(f, w, s)` computes the unmasked sum `f + (w << s) - (16 << s)`. For a row with f, w and shift it is called with the row's shift. For an lfo_dynamic row with f, w1 and w2 it is called for both words at shift 0.
- A sum outside 1..4095 adds the marker `lfo_wrap` to the row's marker set. The existing rule `rule-audio-disputed-mark` then reports `AUDIO_DISPUTED_POINT` for a MAN group, as for f=0. ASSUMED rows are untouched.
- `tests/audio/DISPUTED` and the awk header say that the marker is now found in the row.
- Two tags, `rule-audio-disputed-wrap-static` and `rule-audio-disputed-wrap-dynamic`, so that each statement is removable and detected.

**Deviation (a sum of 0 is flagged).** The review says "below 0 or at least 4096", but its own probe row (`f=16;w=$00;shift=0;k=2;d=8192`) has the sum exactly 0, which is the 0 -> 4096 rule of D-184, not a negative wrap. The lint flags `< 1` and `> 4095`.

**Controls (all in the existing tests/audio mini-root style):**
- `disputed-wrap-zero`: the review probe, sum 0. `-low`: f 1, w $00, shift 2, sum -63. `-high`: f 4095, w $1F, sum 4110. `-dynamic`: f 8, w1 $18, w2 $00, sum -8. Each gives exactly one violation, `AUDIO_DISPUTED_POINT`.
- `ok-lfo-bounds` (must pass): sums 1 and 4095 for lfo_static and 1 and 32 for the lfo_dynamic pair, so the edges are not false positives.
- Two selftest lines: `mutation-audio-rules disputed-wrap-zero` and `disputed-wrap-dynamic`.

**Proof:**
- A copy of scripts/ with the pre-fix awk reports nothing on all four negative mini-roots (`EXPECT_MISMATCH wanted 'AUDIO_DISPUTED_POINT' got ''`). The review's gap is reproduced and closed.
- `sh scripts/audio-check` on the repository is unchanged (files 3, scenes 16, groups 111, rows 251): every committed row is wrap-free (F' 520, 544, 640, 512 and the pair 200 and 184) and still passes.
- A deliberately wrong EXPECT on `disputed-wrap-zero` turns the audio-check stage red (the mini-roots are picked up by `run_controls`).
