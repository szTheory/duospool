# Phase 04.1 - Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

Scope: the threat registers of plans 04.1-01, 04.1-02 and 04.1-03 (T-04.1-01 to T-04.1-10, 10 threats), and a re-check of the Phase 4 residuals AR-01 to AR-08 of 04-SECURITY.md.

Evidence basis (HEAD 22a55eb, working tree clean except the untracked state.json):
- The code (src/core/vid.c, beam.c, ds_vdc.h, vdc.c, constants.def, snapshot.c), the case files, the vexp and checks files, the toy, the ledger, README and docs/ci-timings.md were read directly. Line numbers refer to the working tree at audit time.
- The auditor ran the full gate: `sh scripts/check --timing` gave CHECK RESULT PASS (57 stages; conformance 92 s, sanitizers 192 s). build/gate/results.txt: 330 RESULT lines, all pass; build/sanitize/results.txt: 328 pass (the two sanitize exclusions), every sprite case among them; controls.txt: `CONTROL vid-spr-limit RED_OK`.
- The auditor ran eleven selftests, all PASS: mutation-control-anchor, mutation-video-rules, mutation-video-lex, mutation-sweep-vacuous, mutation-toy-filter, mutation-docs-claim-word, mutation-supported-rule, mutation-restore-skip-field, mutation-tiling-entry, mutation-policy-diff, mutation-fixture-lint-ocr.
- `sh scripts/audit-history --range f9d9d69..HEAD`: clean (15 commits, 106 blobs, 2,080 blob-path pairs). No PDF, image or ROM file is tracked.
- Scratch experiments (outside the repo, never committed): one harness built from src/core with clang -fsanitize=address,undefined -fno-sanitize-recover=all, fed the images spr-basic, spr-limit and vdc-stat (sha256 equal to their manifests).
- Experiment A: 36,000 direct calls of ds_vid_sprites and ds_vid_render on a booted instance whose sprite inputs were set beyond every restore rule: random and extreme SATB words (X and Y 0, 1F, 20, 3F, 1FF, 3FF, FFFF; PC 7FF and FFFF; CGX 1; CGY 0 to 3), random VRAM, CR with SB, HSR and HDR up to FFFF, display_k up to FFFF, lat_div 0 to 255.
- Result of A: no sanitizer report; rec_bytes at most 2792, slots at most 16, covering at most 64, flags 0 or 1, every payload index at most 1FF. The output struct and record were heap blocks of the exact size, so an overrun would have been reported.
- Experiment B: 1,800 hostile snapshots (SATB rewritten, up to 64 VRAM bytes, one VDC0 register, CR with SB and both sprite enables, sprite_pend 0 to 5) restored and run 400,000 clocks with a vid sink (some 3,000 bytes). 1,035 accepted, 765 refused.
- Result of B: every refusal left the target byte-identical, every accepted restore re-serialised to the same bytes, no sanitizer report.
- Experiment C (restore cross-field check): sprite_pend 3 with CR bits 0 and 1 set, restored at a stop where the EV_RCR of a non-display line is next. 37 of 37 were accepted; in 35 the next EV_RCR raised OR or CR where the unmutated restore did not. See U-01.
- Experiment D (invariance with sprite_pend live): spr-limit under zero, seed 1 and seed 2, in chunks of 7, 1364, 1366, 3072 and 357630 clocks, with and without a vid sink. At every stop with sprite_pend non-zero it took a snapshot and continued in a fresh restored instance (139,722 restores).
- Result of D: the final snapshot of every chain equals the uninterrupted run byte for byte (0 differences).

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| Guest SATB contents to the renderer | 64 entries copied in by the SATB DMA (or restored), read by ds_vid_sprites at every EV_LINE | Guest-chosen coordinates, pattern codes, sizes, flips, palettes |
| Guest SATB and HSR/HDR to the slot scan | Display width and blanking fields set the search count and the slot count | Guest-chosen counts and widths |
| Sprite state to the status register | sprite_pend raises OR and CR through ds_vdc_flag at EV_RCR | Status bits, IRQ1 level |
| Restore stream to the instance | BEAM sprite_pend and the SATB, VRAM and VDC0 regions of a caller snapshot | Untrusted bytes |
| Gate configuration to the evidence | Cost levers change policies and schedules of existing cases | Breadth of evidence |
| Project claims to readers | README sprite paragraph, ledger tiers, verification inputs | Support claims |

## Unregistered Flags

SUMMARY Threat Flags sections say "None" beyond each plan's register. The audit found the items below. None is blocking.

| Item | Severity | Note |
|------|----------|------|
| U-01: restore accepts sprite_pend 1 to 3 in any beam state | low | dec_beam only checks `sprite_pend > 3` (snapshot.c:709). A live run has non-zero sprite_pend only on a display line (v_state 1) between its EV_LINE and EV_RCR (beam.c:238, 283). A hostile snapshot can set OR or CR (and IRQ1, if CR bits 0 or 1 are set) once, at the next EV_RCR of a non-display line (experiment C: 35 of 37). |
| U-01 (impact) | low | The effect is bounded: one status bit, gated by the CR enables, and overwritten at the next EV_LINE. There is no memory effect and no hang (experiments B and C under sanitizers). It is the same class as AR-01 (unreachable beam states). Suggested rule: refuse sprite_pend != 0 unless v_state is 1 and stage is not 0, with a refusal row beside sprite-4. |
| U-02: no gate case restores or chunks a sprite scene | low | The video restore and chunk cases run vce-pal, bg-scroll and random programs, so no stop holds sprite_pend live and the gate does not prove invariance for it. Experiment D shows it holds today (139,722 restores, 0 differences). Adding a sprite fixture to one such case would close it. |
| U-03: stale finding in 04.1-03-SUMMARY.md | info | The Findings paragraph says LED-VID-0013 is promoted. LED-VID-0013 has been assumed since 7b4a81f (status line 13) and is not in the README list. This is a planning artifact and not a support claim. |
| U-04: OR and CR as IRQ1 not asserted | info | spr_limit and vdc_stat poll the status register (04.1-02 Deviation 3), so IRQ1 delivery of the sprite flags rests on the shared ds_vdc_flag path judged for RR and VD. README makes no IRQ claim for sprites. |
| Phase 3 IN-03 (ds_run request or result overlapping the instance) | low | Carried from 03-SECURITY.md and 04-SECURITY.md; unchanged by this phase. |

No obvious missed high-severity item was found.
