# Pitfalls Research

**Domain:** PC Engine / TurboGrafx-16 emulator (DuoSpool), evidence-first, headless-core-first
**Researched:** 2026-11-09
**Confidence:** MEDIUM overall. Source-code and changelog evidence is HIGH where a primary file was read directly. Hardware-timing claims are MEDIUM at best because the best prose documents are single-author reverse-engineering notes with explicit uncertainty. Several hardware questions are UNKNOWN and are listed as such.

## How to read this file

Every claim carries one label so the roadmap can tell fact from folklore (per AGENTS.md):

| Label | Meaning |
|-------|---------|
| **[SRC]** | Source-backed fact: stated in a primary or author document read for this research (URL given) |
| **[CODE]** | Code observation: read directly in another emulator's source. It shows what that emulator does or hacks around, NOT what the hardware does |
| **[HIST]** | Historical report: changelog line, issue, or forum post. Real, but second-hand and may be stale |
| **[PROP]** | Proposal: my recommendation or inference for DuoSpool. Not a fact about hardware |
| **[UNK]** | Unknown / conflicting evidence. Needs a hardware test, a primary manual, or an owner decision |

Confidence tags (H/M/L) are my judgement of the evidence quality. They are not output of the `classify-confidence` seam; I used direct WebFetch/WebSearch rather than the `research-plan` seam, and did not cache digests. Roadmap should treat anything not [SRC]+H as "verify at the phase that needs it".

Phase names used for mapping: **Scope/Profile**, **Fixtures/Rights**, **Harness**, **Core CPU**, **Video**, **Audio**, **Input**, **Content/Security**, **Packaging**, **CI/Perf**.

## Critical Pitfalls

### C1: Treating hash agreement, title screens, or emulator-to-emulator agreement as correctness

**What goes wrong:** A golden framebuffer/audio hash, a boot to title screen, or "matches Mednafen/MAME" gets recorded as a PASS for hardware accuracy. The reference emulators themselves disagree with each other and with hardware.

**Why it happens:** Hashes are cheap, and PC Engine has very few independent hardware-verified test ROMs, so the temptation to use "another emulator" as the oracle is strong.

**Evidence the references disagree:**
- Geargrafx issue #115 (Cadash status screen jitter): "Mednafen PCE shows the same problem, but its fast core doesn't" [HIST, M] (https://github.com/drhelius/Geargrafx/issues).
- Geargrafx issue #125 (Burai II sprite glitch): Mednafen and MAME do not show it [HIST, M].
- MAME's own header lists Cadash "jiggles" and Fighting Run has colour/sprite issues [CODE, H] (https://github.com/mamedev/mame/blob/master/src/mame/nec/pce.cpp). All three MAME PC Engine/TG-16/SuperGrafx drivers are flagged `MACHINE_IMPERFECT_SOUND` [CODE, H].
- Mednafen's own VCE code contains `FIXME, this is wrong` on mid-frame pixel-clock changes and `THIS IS BROKEN!` on CD event timing [CODE, H] (https://github.com/libretro/beetle-pce-libretro/blob/master/mednafen/pce/vce.cpp).
- TASVideos: PCEjin bundles Mednafen 0.8.x PCE core; 0.9.x "has some significant changes to PCE". Per-game frame counts differ from console by 10-12 frames (Cadash) across emulators [HIST, M] (https://tasvideos.org/Forum/Posts/331259).

**How to avoid:**
- [PROP] Every acceptance record carries an explicit evidence tier: `repeatability-only`, `vector (documented)`, `differential (disagreement finder)`, `authored-diagnostic with independent verdict`, `hardware-measured (setup+uncertainty recorded)`. Only the last three can back a "correct" claim.
- [PROP] Use differential comparison only to find disagreements; each disagreement gets a triage note, never an auto-update of the golden.
- [PROP] A golden hash must be accompanied by a semantic assertion (register value, RAM byte, on-screen diagnostic verdict decoded from raw video) that would fail if the hash were regenerated from a broken core.

**Warning signs:** Test names like `renders_title_screen`; golden files regenerated by a `--update` flag in the same commit as the code change; compatibility list in README; issue text "matches Mednafen".

**Phase:** Harness (policy) + Fixtures/Rights (diagnostic ROMs). Establish before the first golden is committed.

### C2: Scripted input that the guest never actually consumes

**What goes wrong:** A test presses Run/I/II, the screen does not change, and either the test passes vacuously (no-input and input runs both hash the same) or the failure is misattributed to the core. On PC Engine the input path is a multi-step guest protocol, not a latched register, so it is easy to be "pressed" yet never read.

**Why it happens (PC Engine specifics):**
- The joypad is read through the I/O port by toggling SEL (and CLR); SEL high returns directions (active-low), SEL low returns buttons; games insert a short delay after changing SEL before reading [SRC, M] (https://github.com/asterick/TurboSharp/blob/master/Text/pcetech.txt, author-caveated; https://github.com/pce-devel/PCE_Controller_Info/blob/main/README.md, M-H).
- Scans normally happen "during or right after the VSYNC interrupt" [SRC, M, PCE_Controller_Info]. A button held only between two scans is lost; a script keyed to host frame count rather than guest scan will race.
- 6-button pads alternate scans and the device infers which scan it is by counting CLR pulses; detection code "should scan twice" and not assume which scan returns `0000`. Mouse detection looks for `0000` in the direction nibbles; mouse state machine times out at ~550 us (SEL) / ~600 us (CLR) [SRC, M, PCE_Controller_Info].
- CLR high forces D3-D0 to read 0; unconnected multitap ports return `$0F` [SRC, M, pcetech].
- LibFuturo samples a 32-bit mask at advance start [SRC from project bootstrap]; a guest that reads mid-frame sees only that sample. That is fine for a first slice but must be a stated decision [PROP].

**How to avoid:**
- [PROP] Every input test pair: (a) no-input control, (b) wrong-button control, (c) correct input, with distinct *semantic* outcomes (e.g. fixture writes a RAM byte or draws a glyph only when the right button was read). Harness asserts (c) != (a) before trusting (c).
- [PROP] Record in the observation stream the *guest-side read events* (I/O port reads of the pad with SEL/CLR state) so "input consumed" is observable rather than inferred.
- [PROP] Express scripted input in machine time (master-clock ticks or scanline/frame + offset), not host frames; keep the host-frame mapping in the host layer.
- [PROP] Authored diagnostic fixture must implement the documented two-scan 6-button detection and a multitap scan before any claim about those peripherals.

**Warning signs:** Same hash with and without input; test passes when button mask is zero; input test only exercised through a host wrapper.

**Phase:** Input + Harness. Negative controls must exist before the first input test is accepted.

### C3: Frame-level execution hides raster behaviour; geometry is not constant

**What goes wrong:** Core is built as "run one frame, fill a fixed-size buffer". PC Engine games change horizontal resolution and sometimes vertical timing *within* a frame, use raster-compare interrupts (RCR) to split the screen, and the dot clock is selected by the VCE per mode. A fixed-geometry RGB frame misrepresents the machine and makes raw-video evidence unreproducible.

**Evidence:**
- VCE divides the master clock by 2, 3 or 4 giving 10.8, 7.16, 5.36 MHz dot clocks [SRC, M, pcetech; the same doc's register section says 7/5 MHz, i.e. it is internally inconsistent, so [UNK] for register encoding]; HBlank is not affected by the dot-clock selection [CODE, H, Mednafen vce.cpp].
- Mednafen's VCE comments list overscan width math 256 / 341.3 / 512 per dot-clock class and concede mid-frame pixel clock changes are wrong in its model [CODE, H].
- Games that change resolution mid-frame: Order of the Griffon portraits (Geargrafx #7) and Metal Stoker resolution change on hit (Geargrafx #74) [HIST, M].
- MAME's VDC notes a ccovell "splitres" test where "not all sections seem to be aligned properly" [CODE, H, https://github.com/mamedev/mame/blob/master/src/devices/video/huc6270.cpp].
- Frame rate is "slightly variable" (TASVideos, Mednafen user) [HIST, M]; pcetech says 263 lines/frame with 242 active, while MAME TODO says "Add 263 line mode", i.e. line count is variable by VDC register programming [SRC/CODE, M].

**How to avoid:**
- [PROP] Define the core's native video observation as *per-scanline records* (line number, dot clock, active width, indexed pixel data or 9-bit RGB per pixel) before any frame composition. A "frame" is a derived view.
- [PROP] Schedule on a master-clock timeline (21.477 MHz-derived; confirm in manual) with CPU = master/3 or /12 by speed mode, VDC/VCE dot clock = master/2,3,4. Do not schedule in whole frames or whole scanlines until proven sufficient by a named game/test [PROP; clock ratios are from pcetech M, verify against HuC6260 manual].
- [PROP] Early decision (open question #4 in EMULATOR-DNA): is input sampled at advance start sufficient? Document the proven limit; do not promise raster-timed input.

**Warning signs:** A `FRAME_WIDTH = 256` constant in the core; `run_frame()` as the only step primitive; tests that cannot express "stop at scanline N"; palette stored as host RGB rather than 9-bit VCE entries.

**Phase:** Video (+ Scope/Profile for the granularity decision). Architecture-shaping; get wrong and it is a rewrite.

### C4: Treating community timing documents as an oracle

**What goes wrong:** `pcetech.txt`, `sgxtech.txt`, and emulator comments are used as the spec and each sentence becomes a test expectation.

**Evidence:**
- pcetech.txt: the author warns "my testing methods or interpretations ... could be flawed"; many items are explicitly hedged ("I think the CPU treats zero as a 'no change' value"; "I have not figured out exactly how this works"; "isn't known if either instruction takes more or less time when switching between different speeds") [SRC, M] (https://github.com/asterick/TurboSharp/blob/master/Text/pcetech.txt). It asks for credit to Charles MacDonald [SRC].
- sgxtech.txt: "in a very preliminary state"; EXT BUS /OE modification "not know if all units have this"; unknown whether any software uses S-EXP [SRC, M] (https://github.com/MiSTer-devel/TurboGrafx16_MiSTer/blob/master/docs/sgxtech.txt).
- MAME h6280 header says "csh, csl opcodes are not supported" while the opcodes are implemented later, and "I am unsure if flag B is set upon execution of rti" [CODE, H]. Stale comments are common.
- Mesen2's VRAM-delay commit says "All of this is guesswork based on results from a test rom" and "probably not quite right" [CODE, H] (https://github.com/SourMesen/Mesen2/commit/b84d4f23cff067209531ab652e3f6b33438a1163).

**How to avoid:**
- [PROP] Maintain a *claim ledger*: each hardware behavior = statement + sources + disagreement + status (`spec`, `measured`, `inferred`, `guessed`) + the test that pins it. Code comments cite ledger IDs.
- [PROP] Require two independent sources (manual + measurement, or measurement + independent implementation that is not a port of the same code) before moving a behavior to `measured`. Mednafen, beetle-pce, Geargrafx and BizHawk share lineage; do not count them as independent.
- [PROP] Locate primary manuals early. The Hudson HuC6280 hardware manual PDF exists (mirrored at https://www.cpcwiki.eu/imgs/9/97/HuC6280_-_CMOS_8-bit_Microprocessor_Hardware_Manual.pdf [SRC, M for existence; contents not read here]); HuC6260/HuC6270 manuals are reported on the same page but were not retrieved [UNK]. Redistribution rights of those PDFs are [UNK]; cite, do not vendor.

**Warning signs:** Test expectations whose only justification is a pcetech sentence; "TODO verify" comments copied from another emulator.

**Phase:** Scope/Profile (ledger) -> every hardware phase.

### C5: HuC6280 timing and quirk handling (T flag, block transfers, IRQ latency, timer, speed switching, wait states)

**What goes wrong:** A "65C02 plus a few opcodes" core passes instruction vectors yet breaks games. The HuC6280 differs from the 65C02 in cycle counts, the T flag, block transfers, the MMU, an on-chip timer and a two-speed clock.

**Facts and reports (all CPU-level; mixed confidence):**
- **T flag:** cleared on each instruction fetch; set by SET or by PLP with bit 5; RTI preserves it; interrupt entry pushes P and the handler clears T; BCD with ADC needs SED before SET [SRC, M, pcetech]. MAME added T flag "fixes PCE Ankuku Densetsu title screen", later ADC T-flag Z-flag fix and +3 cycles for T-mode ADC/AND/EOR/ORA/SBC [CODE/HIST, H, https://github.com/mamedev/mame/blob/master/src/devices/cpu/h6280/h6280.cpp]. Mednafen: "Combined cycle total of TPREFIX and TPOSTFIX must be 3" [CODE, H]. T-flag memory operand uses zero page at logical `$2000+X` [CODE/SRC, M].
- **Block transfers (TAI/TDD/TIA/TII/TIN):** length 0 = 65536 bytes; cycle formula `6*l+17` in MAME's table; push Y,A,X / pop X,A,Y; "cannot be interrupted" per pcetech [SRC, M]. MAME fix: "Taking of interrupts is delayed to respect a pending instruction already in the instruction pipeline; fixes After Burner", with a follow-on "improvements to delayed interrupts" [HIST, H]. Mednafen comment: "Needed so a BMT isn't interrupted" [CODE, H]. **[UNK]**: exact IRQ latency around a block transfer and after CLI/RTI relative to the next instruction is not measured in any source I found.
- **Timer:** 7-bit, ticks every 1024 cycles of the 7.16 MHz clock independent of CPU speed; fires on underflow; acknowledged by writing `$1403`; the enable bit does not mask the line, and unacknowledged interrupts re-fire after every instruction [SRC, M, pcetech]. MAME history: single-shot timer "fixes Crude Buster music in level 1", then reverted to periodic; reload "latched only with 0->1 counter enable transition"; stop->start reloads [HIST/CODE, H].
- **Interrupt priority:** MAME: Timer highest, then IRQ1, then IRQ2 [HIST, H]. IRQ mask bits for IRQ1/IRQ2 were once swapped in MAME (v1.03) [HIST, H]. BRK uses the IRQ2 vector [SRC, M].
- **Speed switching:** power-up in low speed (1.79 MHz); CSL/CSH are 3 cycles; unknown whether cycle count differs when switching [SRC, M, pcetech; UNK for switching case]. Mednafen: speed change "takes effect for the last CPU cycle of CSL/CSH. Be cautious not to change the order" [CODE, H].
- **Wait states / bus stealing:** every VDC/VCE access costs +1 cycle (pcetech, MAME v1.10, Mesen2); ST0/ST1/ST2 effectively 5 cycles [SRC/CODE, M-H]. Mesen2 notes the VRAM stall is "not always a multiple of three master clocks" [CODE, H].
- **MPR/MMU:** at power-up MPR7 = 0, others random; TAM with operand 0 writes nothing; TMA #0 behavior unknown [SRC, M, pcetech; UNK]. ST0-ST2 write to VDC at physical `$1FE000-$1FE003` without MMU translation (forum summary) [HIST, L].
- **Misc:** branches crossing page/8K boundary add no cycle; illegal opcodes act as 2-cycle NOPs; RMW has no dummy cycles [SRC, M, pcetech; not measured against other sources].

**How to avoid:**
- [PROP] Build CPU in two layers: (1) opcode/flag/cycle vectors from the manual's tables, tagged by source; (2) interrupt-timing and block-transfer behavior as *named profile parameters* with explicit [UNK] status until a measurement exists.
- [PROP] Write authored diagnostic fixtures that *measure* the thing from the guest (timer read-back, T flag, TAM/TMA round trips, block-transfer length-0, interrupt-after-block-transfer ordering) and record outputs to RAM; the verdict is the literal expected value from manual/measurement, not from DuoSpool.
- [PROP] Do not chase After Burner/Crude Buster-class game behavior until the primitive is unit-tested; log those games as *hypothesis cases* in the ledger.

**Warning signs:** Core passes 65C02 vectors but no T-flag/TAM/TMA tests; timer implemented without enable-edge reload latch; interrupts serviced mid-instruction; speed mode not part of cycle accounting; IRQ priority hard-coded without a source.

**Phase:** Core CPU. HuC6280 vs 6280A CPU differences beyond PSG are [UNK].

### C6: VDC (HuC6270) timing: VRAM access windows, DMA, VBlank/RCR, sprite limits, burst mode

**What goes wrong:** The VDC is implemented as "registers + frame renderer". Games depend on CPU stalls during VRAM access, DMA completion interrupts, the exact scanline a VBlank/RCR interrupt fires, sprite-overflow flag semantics, and mid-frame register writes.

**Facts and reports:**
- **VRAM access:** BSY status bit "set when VDC is waiting for a CPU access slot during the active display area" [SRC, M, pcetech]. Mesen2: SATB/VRAM DMA blocks transfers; in VBlank/forced blank/sprite-fetch-disabled, access every other dot; during rendering only free CPU slots; "all guesswork from a test rom"; fixes Wonder Momo; D&D Order of the Griffon breaks without the wait on status read [CODE/HIST, H].
- **VRAM write during DMA:** Mednafen 0.8-era hack "games that try to write to VRAM while VRAM DMA is in progress" (fixes Crest of Wolf) and it "doesn't fix the underlying issue"; pceDev fork later changed when the burst bit is latched, and made MWR timing optional (`pce.mwrtiming_approx`) [HIST, M] (https://github.com/pce-devel/mednafenPceDev/releases).
- **DMA:** MAME TODOs: "Fix timing of VRAM-SATB DMA", "Implement VRAM-VRAM DMA", "DMA speeds differ depending on the dot clock" [CODE, H]. pcetech: SATB DMA end interrupt four scanlines after the active period; VRAM-VRAM DMA halted (not aborted) if active display starts [SRC, M, author-hedged]. Areas `$8000-$FFFF` of VRAM address space are open bus/ignored [CODE, H].
- **VBlank/RCR:** MAME: VBlank IRQ at the start of HDW after VDW ends; RCR IRQ near end of HDW; last possible RCR with 240-line VDW is `$130` "confirmed on real HW"; one-line-early VSW latch; `m_vert_to_go` side effects cause "faussete Stage 2 excessive slowdown" and "xwiber Stage 2 boss never spawning" [CODE/HIST, H]. pcetech: first active line is `$0040`, valid RCR `$0040-$0146` [SRC, M].
- **Sprites:** 16 sprite-buffer entries per line, 32-px-wide sprites use two; overflow flag semantics: MAME "flag is set only if irq is taken, Mizubaku Daibouken relies on this" [CODE, H]; MAME TODO "test sprite collision and overflow interrupts" [CODE, H]. Sprite 0 collision against any buffered sprite [SRC, M, pcetech]. Narrow display (<32 chars) drops two sprites at a time from sprite 64 [SRC, L-M, single claim].
- **Burst mode:** clearing both bits mid-active-display does not enable it; it takes effect only if both stay clear through the next frame [SRC, M, pcetech]; latch timing was a bug source (pceDev v1.1) [HIST, M].
- **Sprite alignment:** MAME `select_sprites()` "one line off in alignment" compensation, "cfr. rennybla & draculax" [CODE, H].
- **Known-broken in MAME driver:** Side Arms "totally broken", Violent Soldier intro artefacts [CODE, H].

**How to avoid:**
- [PROP] Model VDC timing as a state machine driven by the master-clock timeline (C3), with hooks: access-slot availability, DMA state, sprite-fetch state. Start with an explicit simplification level (e.g. L0 = no stalls, L1 = fixed stalls, L2 = slot model) and label every claim by level.
- [PROP] Pin each behavior to an authored fixture that records status-register reads and interrupt scanline numbers into RAM. Do not hash frames for DMA/RCR behavior.
- [PROP] Defer VRAM-VRAM DMA, burst-mode details, and sprite-overflow corner cases to a named later slice unless the first fixture needs them; record the deferral as a profile limit rather than a silent gap.

**Warning signs:** VDC register write cost = 0 cycles; DMA instantaneous; interrupts raised at the scanline boundary regardless of HDW/VDW; sprite limit implemented as "64 sprites max" rather than per-line buffer; one global "frame ready" flag.

**Phase:** Video (core of the phase); Core CPU for the wait-state interface.

### C7: Rights: fixtures, GPL test ROMs, HuC library linkage, and commercial-content leakage

**What goes wrong:** A convenient test ROM is vendored with unclear terms; a diagnostic is built with a compiler/runtime whose output licensing is unclear; or CI logs/artifacts leak commercial game content.

**Evidence:**
- 240p Test Suite PCE source header: GPL-2.0-or-later, "compiled with HuC", includes HuC headers (`huc.h`, `res.h`, ...), with conditional `SGFX` and `SYSCARD1` builds [SRC, H] (https://github.com/ArtemioUrbina/240pTestSuite/blob/master/240psuite/PCE/240pSuite.c). Main README: GPL v2 or later; artwork credited (Asher, Konsolkongen) without separate terms stated [SRC, M]. A ROM built from GPL sources is a GPL-covered binary; bundling it creates GPL obligations (corresponding source, notices) on the distribution of that artifact [PROP; legal conclusion needs owner/counsel].
- HuC repository license text, as summarized (not read in full): Simplified BSD only for Ulrich Hecht's 2014 additions; MagicKit assembler "freeware statement in source"; TGEmu and most test cases GPL; "remaining code" terms unspecified [SRC via summary, L-M]. **Action:** read the LICENSE file directly before admitting any HuC-built ROM; a runtime library of unspecified terms is linked into every HuC-built ROM [UNK].
- PCE_Soundtest: MIT, but it is an observational analog test (oscilloscope/Audacity capture) with no stated waveform oracle [SRC, H] (https://github.com/pce-devel/PCE_Soundtest). rgalland/PCEngine_TestRoms: no license file visible, no results [SRC, M] (https://github.com/rgalland/PCEngine_TestRoms).
- MAME legal page: free download does not grant further redistribution rights [HIST, M]. The same principle applies to emulator source: MAME's PCE files are BSD-3 with copyright notices (pce_slot.cpp: Fabio Priuli; h6280.cpp: Bryan McPhail; c6280.cpp: Charles MacDonald) [CODE, H]; Mednafen-derived PCE code is GPL-2.0-or-later [CODE, H].
- AGENTS.md: a hash does not grant redistribution rights [SRC, project].

**How to avoid:**
- [PROP] Fixture manifest fields: `source_repo+commit`, `build_recipe`, `toolchain+version`, `library_licenses`, `output_sha256`, `license`, `notices`, `redistribution`, `test_meaning`, `oracle_tier`. CI fails closed on any fixture without a manifest entry or with `license: unknown`.
- [PROP] Author the first fixtures in a PCEAS (or equivalent) assembly with **no** HuC runtime and your own minimal startup; the source is then yours and the licence is a project decision. Check the assembler's own terms for tool-use constraints (MagicKit "freeware") but do not assume anything about output [UNK].
- [PROP] GPL test ROMs (240p) run only from a private/local corpus or an optional "external suite" job that downloads at run time from the original host; never vendored in the public tree unless the owner accepts GPL obligations for that artifact. Never link GPL fixture *source* into the emulator.
- [PROP] Commercial content: no ROM names, header strings, disc titles, or raw frame/audio dumps in public logs or uploaded artifacts. Private-corpus runs emit only pass/fail class + opaque local IDs, upload nothing, and are not CI-triggered from forks. Guard with a log-redaction test (feed a fake "commercial" fixture and assert no strings appear in output).
- [PROP] Cite MAME/Mednafen as *references*; if code is ever copied, record file, commit, license, notice, and maintenance cost (AGENTS.md). Do not copy Mednafen (GPL) structure into a project whose license is not decided.

**Warning signs:** `roms/` directory in git; `.gitignore` as the only protection; test artifacts named after games; upload-artifact steps with `if: always()` on corpus jobs; a fixture whose "source" is a URL with no commit hash.

**Phase:** Fixtures/Rights (first), CI/Perf (artifact policy). Needs an owner decision on license/visibility before any GPL fixture is admitted.

### C8: Non-deterministic harness and undefined power-on state

**What goes wrong:** Two runs of the same fixture differ, or pass only because uninitialised state happens to be benign.

**Evidence:** At power-up MPR7 is 0 and the other MPRs are "random"; the timer and I/O buffer have an internal last-value buffer for `$0800-$17FF` [SRC, M, pcetech]. RAM (8 KB PCE, 32 KB SGX per Mednafen comment) and VRAM/palette initial contents are not documented in what I read [CODE for sizes, UNK for contents]. Mednafen's PCE frame rate is "slightly variable" [HIST, M]. Host-clock pacing is in the AGENTS.md exclusion list.

**How to avoid:**
- [PROP] Power-on state is an explicit, versioned input: `power_on_seed` plus policy (`zero`, `ff`, `seeded-random`). A fixture must pass under at least two policies, or declare which policy it depends on.
- [PROP] No host clock, thread timing, or floating-point-dependent output in the core. Audio resampling to host rate lives outside the core.
- [PROP] A determinism test runs each fixture twice in a fresh process and once reordered among other tests; all three outputs equal.

**Warning signs:** Flaky test restarts; a fixture that initialises nothing; "run for N ms" measured in wall time.

**Phase:** Harness + Core CPU.

### C9: Skipped or missing checks look green

**What goes wrong:** A required fixture is absent (rights, build failure, private corpus not mounted), the runner exits 0 with "0 tests", or a skip is reported as pass.

**How to avoid:**
- [PROP] Required inventory file listing every expected test ID; harness compares executed vs expected and fails on any missing. Outcome enum: `pass | guest-fail | timeout | harness-fail | skip | cancelled | missing-artifact`. Only `pass` is green; `skip` allowed only when explicitly listed as optional.
- [PROP] Calibrate with a named negative control (deliberately impossible expectation must fail; zero-input run must differ from input run; truncated ROM must be refused).
- [PROP] Private-corpus jobs report `skipped (corpus absent)` as a distinct non-green status on the release gate.

**Warning signs:** CI green after a fixture removal; exit code only; test count not printed; `|| true`.

**Phase:** Harness, CI/Perf.

### C10: HuCard identification heuristics, mappers, and malformed-content handling

**What goes wrong:** A loader that guesses from size or bytes mis-identifies content, silently accepts malformed files, or has an unbounded read/alloc.

**Evidence (MAME `pce_slot.cpp`/`pce_rom.cpp`, BSD-3) [CODE, H]:**
- 512-byte header: detected only when `len % 0x4000 == 512` (and not from a softlist); logged and skipped.
- US/TG-16 bit-reversal: `if (ROM[0x1fff] < 0xe0)` then every byte is bit-reversed (`bitswap<8>(i,0,1,2,3,4,5,6,7)`). No explanation of the `0xe0` threshold.
- Cart type by size/content: `len == 0x280000` -> Street Fighter II mapper (banks via writes to `$1FF0-$1FF3`, four 512 KB windows); Populous identified by string `"POPULOUS"` at `0x1f26`, 32 KB RAM at `0x80000-0x87fff`; CD system card by strings at `0x29d1`/`0x29c4`/`0x3ffb6`; Tennokoe Bank type unimplemented ("`// TODO: type for TENNOKOE`", save data "Not entirely correct", unlock "a complete guess").
- Mirroring for non-power-of-two sizes: special-case maps for 384 KB and 192 KB, a generic mirror fill for others, and a header TODO "reimplement cart mirroring in a better way".
- Loader hygiene: `FIXME: check error return, guard against excessively large files` and `FIXME: check error return or read returning short`; `call_unload()` empty.
- Mednafen identifies SuperGrafx titles by a CRC table (Darius Plus, Aldynes, 1941, Granzort, Daimakaimura, Battle Ace) [CODE, H] and Geargrafx #95 shows "Arcade CD-ROM" forced mode breaks some SuperGrafx CD games (works on Auto) [HIST, M].

**Inference [PROP]:** the `0xe0` test appears to rely on the reset vector high byte being in `$E0-$FF` (MPR7=0 maps ROM bank 0 at `$E000`, reset vector at `$FFFE`). That is my reasoning, not a source claim. A bit-reversed image whose true high byte is `$E7/$EF/$F7/$FF` reverses to a value >= `$E0` and would be missed. Treat any heuristic as "suggestion + explicit override + manifest record", never as truth.

**How to avoid:**
- [PROP] Loader returns a typed result: `{ok(profile, orientation, mapper, size), refused(reason)}`. Refusal reasons are enumerated and tested: size 0, size not a multiple of 8 KB after header strip, > configured max (2.5 MB for SF2 as an explicit mapper case), header/size ambiguity (`len % 0x2000 == 0x200` vs `%0x4000`), unknown mapper, orientation ambiguous.
- [PROP] Ambiguity is a refusal unless the caller states orientation/mapper explicitly (config ID). Do not use game-name/CRC databases to select hardware profiles; record content identity (hash) separately from hardware profile selection.
- [PROP] Non-power-of-two mapping is covered by a table of authored fixtures at 192 KB, 384 KB, 512 KB, 768 KB, 1 MB, 2.5 MB, each reading a bank signature through every mirror.
- [PROP] The first slice supports exactly one named orientation and mapper (plain HuCard); every other path returns a distinct `unsupported` result.

**Warning signs:** `if size == X` branches; silent byte-swap on load; ROM "padded" to a power of two inside the loader; no max-size constant; short read treated as success.

**Phase:** Content/Security (+ Fixtures/Rights for the size-matrix fixtures).

---

### C11: Silent scope creep and implicit profile selection (SuperGrafx, CD, Arcade Card, region, CPU revision)

**What goes wrong:** First profile "just works for most HuCards", then SuperGrafx/CD hacks seep into the base path, region and CPU revision are implicit, and a profile claim means different things in different tests.

**Evidence:**
- SuperGrafx adds a second VDC and a VPC; /IRQ1 is shared so software must read both VDC status registers; mixed resolutions are impossible because the VCE sets the dot clock; priority modes have corner cases; Dai Makaimura requires specific priority behavior (Mednafen comment) [SRC, M (sgxtech.txt is preliminary); CODE, H].
- MAME driver notes "IRQ wiring on the SuperGrafx's VDC outputs: needs input merger?" [CODE, H].
- Region bit: I/O port bit 6 is country (1 = PC Engine, 0 = TG-16); bit 7 is CD unit sense; bits 5-4 read 1 [SRC, M, pcetech]. Whether other region/revision differences matter to a *HuCard* profile (CD sense, controller signaling) is [UNK].
- HuC6280 vs HuC6280A: PCE_Soundtest reports a "pop"/DC-offset difference in the original HuC6280 (white PCE and most hardware) and none in HuC6280A (SuperGrafx and some CoreGrafx) [SRC, M-H, analog observation only]. Geargrafx exposes a "HuC6280A audio" option [HIST, M] (https://docs.libretro.com/library/geargrafx). Wikipedia says 6280A "fixed some minor audio issues" [HIST, L].
- Geargrafx claims "accurate emulation supporting the entire HuCard PCE / SGX catalog" [SRC, H for the claim being made; unverified claim]. Do not import that claim.

**How to avoid:**
- [PROP] Profile is a first-class value in every test, manifest, and observation record: `{region, console, cpu_rev, vdc_count, vce_rev, controller, media}`. Unknown fields are explicit `unspecified`, and a test that depends on one fails if unspecified.
- [PROP] SuperGrafx and CD are *separate* components behind the base machine; the base profile is not allowed to compile in their registers. Decision to include them is an owner gate with a named user outcome (AGENTS.md).
- [PROP] Do not auto-detect profile from content hashes; do detect-and-refuse.

**Warning signs:** `is_sgx` flag read inside the HuC6270 code; region as a bool; tests labelled "PCE" without a console revision.

**Phase:** Scope/Profile.

---

### C12: Premature generic bus / public API / early LibFuturo adoption

**What goes wrong:** A generic `Bus` trait or C ABI is frozen before a consumer exists, then fights HuC6280 realities.

**Why it bites here specifically [PROP, built on source facts]:**
- HuC6280 address translation is MPR-based 8 KB banks (8 registers), TAM/TMA are CPU instructions, zero page/stack are at fixed logical `$2000-$21FF` [SRC, M]; ST0-ST2 bypass the MMU to the VDC [HIST, L]; the I/O page has an internal last-value buffer [SRC, M]; VDC/VCE access injects CPU stall cycles that depend on VDC state [SRC/CODE, M-H]; Mednafen notes its CPU "can only handle PC going about 8192 bytes over" [CODE, H]. A generic read/write(addr) trait with no cycle feedback cannot express any of those.
- LibFuturo specifics recorded in the project (32-bit button mask sampled at advance start; single content span; gray8/RGB24/index8 video; S16 audio) are potential mismatches with variable geometry (C3), HuCard + system card + CD tracks, and raster-timed input [SRC, project bootstrap].

**How to avoid:**
- [PROP] The CPU core talks to a concrete `Machine` interface that returns `(value, extra_cycles)`; abstract only after two consumers exist.
- [PROP] Headless runner + one installed-consumer proof first; write an adapter prototype or document a concrete failing case before proposing any LibFuturo contract change (AGENTS.md).
- [PROP] Keep API/ABI, state format, save/media format, behavior revision, content identity, and hardware profile as separate version axes only when each appears.

**Warning signs:** `trait Bus` before the second chip exists; public header committed before the first consumer; structs with reserved padding "for later".

**Phase:** Scope/Profile + Packaging.

## Moderate Pitfalls

### M1: PSG (HuC6280 sound) modelled as a plain 6-channel wavetable

**What goes wrong:** Sound is "close" but misses DDA, LFO, noise, and write-order behavior, or audio checks only assert a nonzero buffer.
**Facts:** DDA bit 1->0 transition resets waveform index; waveform writes accepted only when channel enable and DDA are clear [SRC, M, pcetech]. MAME `c6280.cpp` [CODE, H, BSD-3, Charles MacDonald]: open items "Verify LFO frequency from real hardware", "Noise generating algorithm is shared in all channels?", "wave pointer is increased at writing data when sound playback is off??"; volume range 48 dB over 32 steps. Mesen2: LFO modulates channel 1 period from channel 2 output with shifts (1, 4, 16) [CODE, H]; only channels 5/6 have noise [CODE, H]. pcetech says effective PSG clock 3.58 MHz even though patents say 7.16 [SRC, M, author conclusion; UNK]. Community accuracy debate (Ootake vs MAME "brighter, lacks LFO") is opinion [HIST, L].
**Prevention:** [PROP] Observe PSG as a *register-event log + per-channel sample stream* before mixing; fixtures check literal waveform data/period/index against a documented formula, not a perceptual check. Mark LFO/noise/write-while-off as `unverified` profile fields. Analog HuC6280 vs 6280A DC offset is a hardware-capture claim: out of scope for deterministic tests unless an oscilloscope/capture setup with uncertainty is recorded (owner gate for physical hardware).
**Warning signs:** audio test = "buffer not all zeros"; one golden WAV; mixer pre-scaling baked in the core.
**Phase:** Audio.

### M2: Joypad protocol shortcuts (SEL/CLR, 6-button, multitap, region bit)

**What goes wrong:** Pad modelled as a latched 8-bit value; multitap/6-button/mouse protocols break; known multitap-incompatible titles misdiagnosed.
**Facts:** See C2. Youkai Douchuuki shows a black screen with a multitap attached (real-hardware incompatibility, not an emulator bug) [SRC, M, PCE_Controller_Info]. MAME's `joypad6.cpp` models a CLR-clocked 2-bit counter (74xx163) selecting button sets and autofire; TODOs: "Verify DTC114Y function for slow motion in Avenue Pad 6" [CODE, H]. The bundled white PCE pad has no autofire (MAME comment) [CODE, M]. Turbo/autofire is a host-side feature; do not put it in the core [PROP].
**Prevention:** [PROP] Implement the port as a CLR/SEL state machine with per-peripheral state; add a "known hardware incompatibility" note class so a failing multitap title is not counted as a bug without evidence.
**Phase:** Input.

### M3: Special mappers and backup devices treated as afterthoughts

**What goes wrong:** SF2 mapper, Populous 32 KB RAM, Tennokoe Bank (Memory Base-like), Arcade Card and CD RAM overlays bolted on with size heuristics.
**Facts:** C10. Also Super System Card RAM at banks `0x68-0x7F` (192 KB), CD unit RAM at `0x80-0x87` (64 KB), Memory Base 128 uses CLR as a clock with `$A8` magic bit pattern LSB-first [CODE/SRC, M-H].
**Prevention:** [PROP] A mapper is a declared profile component with its own manifest and fixture; the loader refuses unknown mappers; no mapper work in the first slice.
**Phase:** Content/Security (later slice).

### M4: VCE palette and colour output conflated with host RGB

**What goes wrong:** 9-bit GRB palette converted to host RGB in the core; background/sprite palette halves, mid-line palette access glitches and "blur" bit lost.
**Facts:** 512 9-bit entries, background first 256, sprites remaining 256; CPU access mid-line repeats the last pixel colour; bit 2 "blur" is unexplored [SRC, M, pcetech; blur = UNK].
**Prevention:** [PROP] Raw observation = 9-bit VCE colour index/value per pixel; conversion is a documented host transform with its own tests; do not encode a particular RGB table in the core.
**Phase:** Video.

### M5: Hardware-oracle gap: no known independent CPU/VDC conformance suite

**What goes wrong:** The team assumes a ready-made test-ROM ecosystem (like NES/GB) exists.
**Facts:** My searches found no HuC6280 instruction-test ROM or VDC timing suite with a confirmed licence; found 240p Test Suite (display), PCE_Soundtest (analog), rgalland tests (unlicensed), ccovell splitres (referenced by MAME; location/licence not found) [SRC/HIST, M-L]. Mesen2's VRAM timing was tuned from "a test rom" whose identity is not stated [CODE, H].
**Prevention:** [PROP] Budget for authoring original diagnostic fixtures plus a small hardware-measurement programme (owner gate) instead of assuming oracles exist. Record in Scope/Profile which behaviors have no oracle.
**Phase:** Fixtures/Rights, Harness.

### M6: Copying another emulator's structure, license, or comments

**What goes wrong:** Mednafen's cycle model, MAME's device layout, or Mesen2's timing guesses become the architecture; licences (GPL-2.0+ / BSD-3 / GPL-3 [UNK for Mesen2/Geargrafx; verify]) leak in; "FIXME" guesses are inherited as facts.
**Prevention:** [PROP] Clean-room rule: read behavior, write own implementation; any copied helper gets provenance + licence + notice + maintenance cost (AGENTS.md). Keep a "do not inherit" list (e.g. the stale h6280 header notice, Mednafen "HORRIBLE" workarounds).
**Phase:** Scope/Profile (policy), all implementation phases.

### M7: Save/backup data and save-state handling

**What goes wrong:** Save files and save states trusted as inputs; CD save-state restore incorrect; BRAM init bug.
**Facts:** MAME: CD save states "saved but not correctly restored", saving "fine with cart games" [CODE, H]. Mednafen pceDev: BRAM initialization fix cured Sorcerian lockups [HIST, M]. Tennokoe Bank save data "Not entirely correct" [CODE, H].
**Prevention:** [PROP] First slice: no persistent media, no save-state format. When added, validate length/magic/version, keep them in the core as inert data, and test refusal paths.
**Phase:** Content/Security (later), Packaging.

### M8: Performance work that changes behavior or is measured noisily

**What goes wrong:** Optimising the per-pixel renderer or scheduler changes timing; perf CI on shared runners produces noise; "faster" claims lack workload identity.
**Facts:** MAME TODO "sprite precaching", "rewrite the base renderer loop" [CODE, H] show optimisation pressure on the renderer; Mednafen pce_fast vs pce differ in output (Geargrafx #115) [HIST, M].
**Prevention:** [PROP] A perf run asserts output equality with the correctness baseline (digest + semantic checks) before reporting speed. Perf is nightly/manual until a clean comparison shows stability; track emulated throughput, latency, memory and CI wall time as separate metrics (AGENTS.md).
**Phase:** CI/Perf (after core correctness).

### M9: CI bloat and import of mature-project machinery

**What goes wrong:** Fuzz matrices, multi-OS builds, perf trend jobs, and game-corpus jobs on every PR; long critical path; caches added without measurement.
**Prevention:** [PROP] One local command == fast PR gate; each CI job maps to one failure class; fuzzing, broad compat, and perf are scheduled/non-required until measured; after each CI run record setup/fetch/compile/test times before adding caches. Do not copy sibling CI.
**Phase:** CI/Perf.

### M10: Installed-consumer proof skipped or faked

**What goes wrong:** The "consumer" builds against the source tree; headers or libs leak via include paths; the package works only because the build dir is present.
**Prevention:** [PROP] Consumer built in a separate directory/process with source and build paths absent (empty `PATH` additions, no `-I` into the tree), loading a fixture from the package's own manifest. Package contents listing is a test.
**Phase:** Packaging.

## Minor Pitfalls

- **Hardcoded game-name strings in logs** (e.g. printing the CD header title): leaks commercial identity into CI logs. Prevent with the log-redaction test from C7. Phase: CI/Perf. [PROP]
- **Frame-rate assumption of 60 Hz**: frame time is variable with line count and dot clock; use machine time. [HIST, M, TASVideos] Phase: Harness/Video.
- **Raw audio ring-buffer assumptions**: PSG clock/sample cadence must be explicit (3.58 MHz effective per pcetech [SRC, M, UNK]). Phase: Audio.
- **Illegal opcodes** treated as faults: they act as 2-cycle NOPs per pcetech; decide and test, do not abort [SRC, M]. Phase: Core CPU.
- **HES music playback / debugger needs** pulling extra state into the core early (Mednafen: "HES playback depends on these structures being left alone") [CODE, H]. Phase: Scope/Profile; defer.
- **Dot-clock-dependent DMA speed** ignored (MAME TODO) [CODE, H]. Phase: Video.
- **Stale comments**: ignore headers like MAME's "csh, csl opcodes are not supported". Phase: all.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Frame-based `run_frame()` core | Fast first picture | Rewrite for raster/mid-frame behavior; fixed-geometry buffers | Only as a thin wrapper over a master-clock stepper |
| Golden hash with `--update` flag | Quick regression test | Silent baking-in of bugs | Only paired with a semantic assertion; never in the same commit as logic change without review |
| Size/CRC based mapper detection | "Just works" loads | Misidentification, rights-laden game DB | Never for hardware profile; fine as a *suggestion* with explicit override |
| Copy a GPL emulator's table/struct | Time saving | Licence entanglement, inherited bugs | Never without owner licence decision and recorded provenance |
| Core-side RGB conversion | Quick display | Loses raw video evidence | Never in core; host-only |
| Vendoring a free test ROM | Easy CI | Unclear redistribution, GPL obligations | Only after manifest shows terms and owner accepts |
| HuC-built fixtures | Faster authoring | Unspecified runtime-library terms | Only after reading the LICENSE and confirming output terms |
| Fixed 8-bit pad value | Simple input | Breaks 6-button/mouse/multitap | Only for a profile explicitly labelled "2-button pad, direct port" |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| LibFuturo | Assume advance-start input and fixed geometry are enough | Build adapter prototype; name mismatch (raster input, variable line width, CD/system-card content spans) with a reproducible case [SRC, project] |
| Reference emulators (Mednafen/MAME/Mesen2/Geargrafx) | Use as pass/fail oracle | Use for disagreement triage only; record version/commit and settings (e.g. `pce` vs `pce_fast`, MWR timing flag) |
| External test ROMs (240p, PCE_Soundtest) | Vendor into repo | Fetch at run time from the origin, hash-pin, record licence; or author your own |
| pcetech/sgxtech | Port statements to expectations | Claim ledger (C4) |
| Hardware capture | Treat capture as ground truth | Record setup, instrument, uncertainty; owner gate before any physical-hardware claim |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Per-dot VDC/VCE simulation everywhere | Low throughput on any host | Optimise only after a named workload profile; keep correctness digest constant | First sub-realtime run on a small host |
| Sprite re-evaluation per line without caching | Hot loop in renderer | Profile first; MAME lists "sprite precaching" as a TODO [CODE, H] | Heavy-sprite scenes |
| Fine-grained scheduler events for timer/DMA | Event queue dominates | Next-event scheduling from the master clock; measured | Long headless runs |
| CI perf on shared runners | Noisy deltas, false regressions | Nightly with workload IDs and uncertainty; non-blocking | Any shared-runner PR gate |
| Rebuilding fixtures on every PR | Slow critical path | Hash-pin fixtures; rebuild only on recipe change | When fixture count > ~20 |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Reading a ROM into an unbounded buffer / trusting the file size | DoS, memory exhaustion | Max size constant; reject before alloc; MAME's own `FIXME ... guard against excessively large files` shows the gap is real [CODE, H] |
| Short read treated as success | Partial ROM mapped, UB-adjacent behavior | Check read length; MAME `FIXME ... read returning short` [CODE, H] |
| Header-strip arithmetic on untrusted lengths | Off-by-N maps, OOB reads | Typed loader result (C10); fuzz the loader with size sweeps (scheduled, not PR-blocking) |
| Mapper/mirror tables indexed by file size | OOB read on odd sizes | Table-driven, bounds-checked bank map; 192/384 KB tests |
| Parsing CUE/CHD/archive paths into fixed buffers | Memory-corruption class seen in libretro-common `cdfs_open_cue_track` (CVE-2025-9809, secondary source) [HIST, M-L, https://vuldb.com/cve/CVE-2025-9809]; snes9x UPS patch OOB write (CVE-2026-39199) [HIST, L] | Out of scope for the first slice; when CD arrives, parse in a separate bounded module, no fixed-size path buffers, reject path traversal and absolute paths in archives |
| Archive handling inside the core | Zip-slip, decompression bombs | Core accepts bytes only; host/archive layer extracts with limits [PROP] |
| Save files / save states trusted | Corrupt state, OOB | Magic+version+length checks, no pointers in state, no-mutation on failed load [PROP] |
| Logging content strings | Rights/privacy leak | Redact; log opaque IDs |
| Fuzzing harness with network or filesystem side effects | Environment dependence | Fuzz target is a pure function over bytes [PROP] |

## "Looks Done But Isn't" Checklist

- [ ] **HuCard load:** often missing refusal paths -- verify empty, truncated, header-only, 513-byte, oversized, and non-multiple-of-8 KB files all produce distinct refusals.
- [ ] **Input test:** often missing controls -- verify no-input and wrong-button runs differ from the correct run semantically, and guest pad reads appear in the observation log.
- [ ] **CPU:** often missing T flag, TAM/TMA, block-transfer length-0, timer enable-edge reload, speed-switch cycle accounting.
- [ ] **VDC:** often missing VRAM stall, DMA interrupt timing, RCR range `$40-$146` behavior, sprite per-line limit with 32-px sprites counting double.
- [ ] **Video evidence:** often missing per-scanline width/dot clock -- verify the observation record is not a fixed-size frame only.
- [ ] **Audio evidence:** often a nonzero-buffer check -- verify register-event log and literal waveform expectations.
- [ ] **Determinism:** often missing power-on policy -- verify two policies and process-restart repeatability.
- [ ] **Fixtures:** often missing licence/toolchain provenance -- verify every fixture has a complete manifest entry and a source-built hash.
- [ ] **CI green:** often a missing-inventory false green -- verify the negative-control gate fails when a required test is removed.
- [ ] **Package:** often tested from source tree -- verify the consumer runs with source/build paths unavailable.
- [ ] **Logs/artifacts:** verify no commercial strings, frames, or audio in public output.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Frame-based core (C3) | HIGH | Introduce a master-clock stepper under the frame wrapper; migrate video observation to per-line records; re-derive goldens with semantic assertions |
| Hash-as-oracle (C1) | MEDIUM | Re-label existing tests `repeatability-only`; add semantic assertions or retire them |
| Fixture licence unclear (C7) | MEDIUM | Remove from tree and history if necessary; rebuild from authored source; update manifest; owner decision on notices |
| Commercial data in CI logs (C7) | HIGH | Rotate/delete logs and artifacts; add redaction test; owner notified (external authority) |
| Heuristic loader misclassification (C10) | LOW-MEDIUM | Switch to refusal + explicit config; add size-matrix fixtures |
| Premature API (C12) | HIGH | Version bump/deprecate; wait for consumer; do not preserve broken shape |
| Perf optimisation changed behaviour (M8) | MEDIUM | Revert; reintroduce with digest-equality gate |
| CI bloat (M9) | LOW | Measure, move jobs to scheduled/non-required, keep one local gate |
